    NetworkPolicy 실습 — 파드 사이의 방화벽¶

    실습 목표¶

    • 쿠버네티스 기본 상태(전부 열림)를 직접 확인한다.
    • NetworkPolicy 원칙(선택 → 기본 거부 → 합집합)을 이해한다.
    • deny-all 패턴으로 네임스페이스를 잠근 뒤 필요한 경로만 연다.
    • 3계층 앱(web → api → db) 격리를 구현하고 검증한다.
    • Cilium 전용 L7 정책(CiliumNetworkPolicy)을 맛본다.

    개념 요약¶

    NetworkPolicy 란?¶

    레이블 셀렉터로 "어떤 파드가 어떤 파드에게 어느 포트로" 통신할 수 있는지 선언하는 L3/L4 방화벽 리소스입니다.

    NetworkPolicy (선언)
       ↓ watch
  cilium-agent (각 노드, DaemonSet)
       ↓ 번역
  eBPF 프로그램 → 커널에서 패킷 허용·차단

    CNI 가 지원해야 동작한다

    Flannel은 NetworkPolicy를 지원하지 않습니다. 이 실습 클러스터는 Cilium을 사용하므로 정상 동작합니다.

    핵심 3원칙¶

    원칙 설명
    선택된 파드만 제한 podSelector에 매칭된 파드만 제한받음. 나머지는 그대로 열림
    선택 = 기본 거부 정책 1개라도 적용되면 그 방향은 화이트리스트 모드
    여러 정책은 합집합 충돌 없음. 하나라도 허용하면 통과

    차단은 DROP, reject가 아니다¶

    정상 응답: HTTP 200 / 연결 성공
차단 결과: timeout (즉시 에러가 아님)
→ 테스트 시 --timeout 을 반드시 지정할 것

    Cilium 상태 확인¶

    kubectl get pods -n kube-system -l k8s-app=cilium

    각 노드에 1개씩 Running 상태여야 합니다.

  --labels="app=web" \

    <!DOCTYPE html> 응답이 오면 기본 상태에서 전부 열려있다는 것이 확인됩니다.

    Step 2. deny-all — 네임스페이스 전체 기본 거부¶

    deny-all-ingress.yaml 파일을 만듭니다.

    # deny-all-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: netpol-lab
spec:
  podSelector: {}          # 모든 파드 선택
  policyTypes:
  - Ingress
  # ingress 필드 없음 = 허용 목록 비어있음 = 전부 차단

    kubectl apply -f deny-all-ingress.yaml

    다시 테스트합니다.

    # 이번엔 timeout 이 나야 정상
kubectl run test-denied -n netpol-lab --rm -it \
  --image=busybox:1.36 --restart=Never \
  --labels="app=web" \
  -- wget -qO- --timeout=3 http://db-svc

    timeout = 차단 성공

    응답 없이 타임아웃이 발생하면 정책이 정상 동작하는 것입니다.

    Step 3. 3계층 격리 — 필요한 경로만 열기¶

    목표 구조¶

    외부 → web(80) → api(80) → db(80)
          ↕ 차단: web 이 db 에 직접 접근 불가

    정책 1 — db 는 api 에서만¶

    # db-allow-api.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-api
  namespace: netpol-lab
spec:
  podSelector:
    matchLabels:
      app: db
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api
    ports:
    - protocol: TCP
      port: 80

    정책 2 — api 는 web 에서만¶

    # api-allow-web.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-web
  namespace: netpol-lab
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: web
    ports:
    - protocol: TCP
      port: 80

    kubectl apply -f db-allow-api.yaml
kubectl apply -f api-allow-web.yaml

    Step 4. 검증¶

    허용 경로 확인¶

    # api 레이블 → db : 성공해야 함
kubectl run test-api -n netpol-lab --rm -it \
  --image=busybox:1.36 --restart=Never \
  --labels="app=api" \
  -- wget -qO- --timeout=3 http://db-svc

    # web 레이블 → api : 성공해야 함
kubectl run test-web -n netpol-lab --rm -it \
  --image=busybox:1.36 --restart=Never \
  --labels="app=web" \
  -- wget -qO- --timeout=3 http://api-svc

    차단 경로 확인¶

    # web 레이블 → db : timeout 이 나야 함 (차단 성공)
kubectl run test-web-db -n netpol-lab --rm -it \
  --image=busybox:1.36 --restart=Never \
  --labels="app=web" \
  -- wget -qO- --timeout=3 http://db-svc

    정책 상태 확인¶

    kubectl get networkpolicy -n netpol-lab
kubectl describe networkpolicy db-allow-api -n netpol-lab

    describe 출력에서 PodSelector와 From 항목이 의도대로 설정됐는지 레이블과 대조합니다.

    Step 5. AND vs OR — 셀렉터 함정¶

    다른 네임스페이스의 특정 파드에서만 허용하는 경우, 하이픈 위치가 동작을 결정합니다.

    # AND — monitoring ns 의 prometheus 파드만
ingress:
- from:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: monitoring
    podSelector:              # <- 앞에 '-' 없음
      matchLabels:
        app: prometheus

    # OR — monitoring ns 전체 또는 같은 ns 의 prometheus
ingress:
- from:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: monitoring
  - podSelector:              # <- 앞에 '-' 있음
      matchLabels:
        app: prometheus

    시험 함정

    - 하나 차이로 AND/OR가 바뀝니다. kubectl describe의 From 항목에서 같은 블록인지 별도 블록인지 반드시 확인하세요.

    Step 6. Cilium 전용 — L7 HTTP 정책¶

    Cilium은 표준 NetworkPolicy 외에 CiliumNetworkPolicy(CNP) 로 HTTP 메서드·경로까지 제어할 수 있습니다.

    # allow-get-only.yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-get-api
  namespace: netpol-lab
spec:
  endpointSelector:
    matchLabels:
      app: api
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: web
    toPorts:
    - ports:
      - port: "80"
        protocol: TCP
      rules:
        http:
        - method: GET
          path: "/.*"

    kubectl apply -f allow-get-only.yaml
kubectl get ciliumnetworkpolicies -n netpol-lab

    Step 7. Egress 제한 + DNS 허용¶

    Egress를 제한하면 DNS(53)도 함께 막힙니다. 서비스 이름으로 통신하는 모든 파드가 즉시 영향을 받습니다.

    # egress-with-dns.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-egress
  namespace: netpol-lab
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Egress
  egress:
  - to:                        # DNS 허용 (필수)
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - port: 53
      protocol: UDP
    - port: 53
      protocol: TCP
  - to:                        # db 접근 허용
    - podSelector:
        matchLabels:
          app: db
    ports:
    - protocol: TCP
      port: 80

    Egress 추가 시 DNS 반드시 포함

    DNS 없이 Egress 정책을 만들면 파드가 살아있어도 서비스 이름을 전혀 찾지 못합니다.

    트러블슈팅 요약¶

    증상 원인 확인 방법
    정책 만들었는데 아무것도 안 막힘 cilium-agent 미동작 또는 레이블 오타 kubectl get pods -n kube-system -l k8s-app=cilium
    허용했는데 여전히 차단 AND/OR 하이픈 위치 오류 kubectl describe networkpolicy 의 From 블록 확인
    port 를 Service port로 씀 파드 포트여야 함 kubectl get svc 의 TargetPort 확인
    Egress 후 서비스 이름 못 찾음 DNS(53) 함께 차단됨 kube-dns로 UDP/TCP 53 허용 추가
    전부 차단됨 ingress: [] 사용 전부 허용은 ingress: - {} (빈 규칙)

    정리¶

    진단 순서:
① cilium-agent Running 확인
② describe 로 selector 가 파드를 골랐는지
③ 파드 포트 vs 정책 port 대조
④ AND/OR 하이픈 위치
⑤ Egress 면 DNS 허용 포함 여부
